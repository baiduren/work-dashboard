# ADR-0004：认证与访问控制（单用户账号 + 密码）

- 状态：**接受（Accepted）**
- 日期：2026-11-02
- 依据：[00 产品概要](../00-product-brief.md) 的部署场景（家里主机、经代理公网访问）

## 背景

早期架构按“仅本机”设计，不做认证。实际部署是家里的主机 + 代理公网访问，必须保证**只有本人**
能看到数据。要求：单用户、登录后可用、退出即失效、公网安全（HTTPS）。

## 决策

在应用内实现 **单用户账号 + 密码 + 签名会话 Cookie**，不引入第三方身份服务：

- 凭据：`AUTH_USERNAME`、`AUTH_PASSWORD` 来自部署环境变量（不入库、不入仓库）；
- 会话：HMAC-SHA256 签名的 Cookie（`HttpOnly`、`SameSite=Lax`，生产 `Secure`），
  载荷含用户名与签发/过期时间，有效期 7 天；换 secret 或改密码即全体失效；
- 访问控制：`middleware.ts` 拦截所有路由，仅放行 `/login`、`/api/auth/login` 与静态资源；
  页面未登录重定向，`/api/*` 返回 401；
- 防护：登录限流、恒定时间密码比较、变更请求校验 `Origin`/`Host`；
- 不建用户表、不开放注册、不做找回密码。

## 备选方案

| 方案 | 不选的原因 |
| --- | --- |
| GitHub OAuth | 需要注册 OAuth App、配置回调，且登录依赖 GitHub 可用性；单用户场景过重 |
| 邮箱魔法链接 | 需要 SMTP/发信服务与域名配置，个人项目维护成本高 |
| 反向代理 Basic Auth（Nginx/Cloudflare Access） | 不改代码也能用，但体验差（无退出/无会话时长控制），且把安全策略散落在部署层 |

## 后果

- 好处：零外部依赖、实现简单、可审计（签名会话）、退出与失效明确；
- 代价：未实现多用户；限流为单实例内存实现，水平扩展时需换成共享存储；
- 运维要求：公网必须经 HTTPS 代理（`Secure` Cookie 依赖 TLS）；`AUTH_SESSION_SECRET` 必须随机且保密；
- 后续若要多人使用：升级为 User 表 + 邀请制，并新增 ADR。
